## [Unreleased]

### Added

- **Whether standings count results against outside clubs can now be set for the whole league, a program or a division, the most specific winning** (`docs/changes/2026-11-13-settings-scope.md`, F11-4a; migration `20261124010000`). A division with no value of its own follows its program, then the league; an explicit "don't count" beats an inherited "count" and the reverse. Each change is audited in the settings trail, and starting the next season copies each program's and each division's value to its copy. The league's value moved over unchanged from the Features page, which no longer offers the switch; the panel that sets the value by level comes in F11-4b. A division's practices a week and practice length can also be saved on their own (`admin_set_division_practice_settings`), without sending its roster rules back.
- **One game can be added by hand on the Games page** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 8, task H1, section 5.5; owner answers of 2026-11-09; no migration). **Add a game** opens a dialog: a division, a home and an away team (an outside club allowed), and either an open slot or a new time (a field, a date, a start and an end). The game is staged into the review as one placed by hand and saved by **Apply** like a move. A new time's slot is found or made first (`ensure_game_slot`, audited when it makes one); a slot the database already had must match the week and times, and if the save then fails the error names the slot it left. A slot holds one game: a slot that already has one is refused, in the hold's words for a Published or scored game, and a new time at an existing slot must keep its end. A team already playing, or a field already in use, at that time, and a slot reserved for another division, are flagged, not blocked (in the dialog, the conflict banner and the saved run's warnings, each clash once). The new game starts not Published, and generating waits while one is staged. Tests: `tests/gameAddByHand.test.jsx` and four scenarios in `tests/e2e/features/published_games.feature`, whose seed slots now carry the wall date and times the database holds.
- **The Import page has a Practices tab: a practice schedule that already exists is uploaded, its names mapped (with an optional alias file), its changes previewed, confirmed and, if need be, rolled back** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 11, section 4.11; no migration). A kind of the Games tab's panel, not a copy. The Edge function `import-validation` stages the whole file in one request (a mirror of core's parse, held to it by a vector table and a Deno test); the preview is the database's dry run, and every count, flag, refusal, hold and probable move on screen is the dry run's own. A team whose saved practices meet the new file's dates is a probable move: its new rows are held back until the admin ticks them ("Tick all probable moves", or one team at a time), and only ticked rows are sent. Division practice settings the file suggests are saved only for a ticked existing division, with the division's other rules kept, and the teams short of their count are counted again after them; a roll back does not undo them. The confirm's stale check runs in the Edge function. Each refusal and flag is said in words (`slot-differs` names what differs), and nothing is created until the confirm's list is ticked.
- **A practice schedule a club already has can be imported, database half** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 10; migration `20261123010000_practice_import.sql`). `map_practice_import_job` stores what the admin decided for each label and which moved rows to add; `apply_practice_import_job(job, dry_run)` previews (every write undone by a sentinel, so the preview is the apply) and applies: slots found by the fields import's key or made unless they would overlap another, each team's practice inserted as manual with no run and only when not already saved (a re-import inserts nothing, an import never changes or deletes a saved practice), every rule broken flagged and never refused (the writer gate's five rules, coach overlap, a team on both halves, a hold over a slot), short teams on the TIME TBD list, and a team's new row held back as a probable move until ticked; `rollback_practice_import_job` refuses after a change and otherwise takes back what it made, keeping anything something references since. The staged row is core's `toStagedPracticeRow`; the allowlist gains `practice_schedule`; the mock mirrors all three RPCs. The Edge function and the Practices tab are PR 11.
- **A games import can record its schedule as the publication baseline** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 6b, task G5, decision 15; no migration). The import's confirm step offers "Record this schedule as the baseline for Changes since publication", ticked when the games arrive Published. After the import is applied, the schedule as it then stands is recorded with the same rows the Exports page records when it uploads its files (one function makes them, over one mapping of the page's inputs), so "Changes since publication" shows no change right after the import and every change from there. A recording that fails is said and the import stands; a roll back says that the import's baseline still describes the imported schedule (a baseline is never changed or removed). "Changes since publication" now reads a game against an outside club (one row of the master export, the club having none of its own) as that game: before, each was unreadable and the comparison could not be read as a verdict.
- **Every page that shows a game reads the saved schedule, and a score can be entered on it** (`docs/changes/2026-11-06-games-table-source-of-truth.md`, F11-3; no migration). The team page and its CSV, XLSX and calendar files, the calendar feed, the Dashboard's count and upcoming list, the Player record, Scores & Results and the Standings page's Recent Games show the games of each season's current schedule (`game_assignments` and `game_scores`), each at its own start and end, so an imported game that ends after its slot shows its real end. Scores & Results and Recent Games hold the first score typed and save both scores of a game together ("Enter both scores"), and say a refused save in words; Scores & Results counts, in one sentence, earlier results whose game is no longer in the saved schedule. A score is a whole number from 0, and a game takes no edit while its score is being saved. With this deployed a league may turn score entry on. Also: the Games page reads the saved schedule again after a save refused for a game's identity; a switch of organization no longer carries the last organization's import job into the Import page; the two fallbacks F11-2 kept for a database without its migration are gone.
- **A game's score is stored against the game itself, a scored game is held where it is, and standings are computed from scores** (`docs/changes/2026-11-06-games-table-source-of-truth.md`, F11-2; migration `20261122010000_game_scores.sql`, with its revert and smoke). `game_scores` holds one row per scored game, keyed by the saved game's id and its two sides (a foreign key with `NO ACTION`, so no writer can delete a scored game or change its teams under the score); `update_game_score` keeps its name and arguments and now names a saved game, takes both scores or none (one without the other is refused), and is still the only writer. A score is entered only on a game of the season's current schedule, and can be cleared even while score entry is turned off. "Held" is one rule, Published or scored: a scored game cannot be moved, cancelled or left out of a save, a regeneration keeps it, a schedule import skips it (`skipped-scored`) and cannot be rolled back over it, each said in the words of a scored game (`game_scored`, `game_scored_omitted`); clearing the score lifts the hold. Deleting a team takes the scores of its games that are not Published with it and counts them. `view_league_standings` is rebuilt over the score table with the same columns and one more, last: an outside club never has a row, and a result against one counts only when the organization turns on **Count results against outside clubs** (Settings, Features; off unless turned on), with the Standings page saying how many results it left out. `current_game_runs` is the one SQL definition of "the schedule" for the pages a later change repoints. **Not in this change:** the Scores, Standings, team and Dashboard pages still read the legacy `games` table (F11-3 repoints them), so on a real database the Scores page has nothing it can score until then; score entry and standings are off unless a league turns them on. Three small changes ride in the same migration: `cancel_ready_import_job` refuses a job that is not `ready_to_apply` (it marked an applied import failed), `get_schedule_tbd` returns a TIME TBD game's date and Game ID, and a time or a Week the games import could not read is now carried into the saved result as a warning.

A TIME TBD game's date is shown with no time on the Games page, in the master export and in the Day Sheet; the Games page's banner names the import's warnings in words; the saved schedule downloads as a file the import reads back with no change. A row with no division or team is refused as a row, a header with a stray space still names its column, and switching organization or season ends the import on screen. - **A game keeps its id when the schedule is saved: a move, a flip or a regeneration updates the game in place, so its Published state and history stay with it** (`docs/changes/2026-11-06-games-table-source-of-truth.md`, F11-1; owner answers of 2026-11-07; migration `20261120010000_game_identity.sql`; rule 14). `persist_game_schedule` updates a game in place when an assignment names it by `id` (a payload row without one is upserted on the matchup tuple, as before; nothing is ever deleted by a save), checks the ids in a fixed order and writes nothing on a refusal (`game_identity_invalid`, `game_identity_repeated`, `game_not_found`, `game_identity_season` for a game stored in another season of the organization, `game_identity_conflict` with both ids), lets two games swap places in one save, and counts a game present in the omission check if its id or its tuple is in the save. `game_assignments.season_settings_id` is set by the save, and `game_is_held` / `game_held_ids` are the one definition of "held where it is" that the guard trigger, cancel, delete team and the omission check ask. The Games page runs `carryGameIds` after the generator (a regenerated game takes the id of the saved game of its pair: the very same place first, then the same week, then the nearest) and sends ids only for saved games; its sentences now say a moved game keeps its history. The mock client mirrors the save and the predicate. The `game-persistence` Edge function answers these refusals, and a game another admin removed a moment before the save was checked, with a 409 `GAME_IDENTITY` carrying the database's words (not a logged failure, except for an id that is not a uuid and a game named twice, which only a page regression can cause and which stay in the failure log). Revert and smoke in `docs/sql/`; no data to move (production holds no games).
- **The Practices page shows, before any run, whether the slots a division may use can hold the practices its teams still lack** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 13 of 13; owner decisions 28 and 29 of 2026-11-06; read-only, no migration, no Edge change). A section at the top, "Before you run: slots against what each division needs", has a row for every division of the season: its teams, the practices they want a week, the saved practices they hold, those still needed, the practice length, the slots it may use (live from today, exactly its length, not closed to it by a reservation) and the room left in them after the saved practices, and a verdict in words: "N to spare", "Short by N", "No slot open" with the reason taken from what refused each live slot (no date left from today, no live slot of the division's length, its slots of that length reserved to another division, or its own reserved slots all out of date so that it may use only those), "Too few weekdays" when the most any one team still needs is more than the open slots can give it on different dates, "None wanted" for a division at 0 a week (never short) and "No teams". A whole-season line counts each slot once though several divisions may use it, and says the rows can add up to more. **It says what its numbers are based on and what they are not:** every open slot a division may use, live from today; that times held outside the app are unknown to it (nothing in the app records one, so it cannot leave one out); that each verdict is an upper bound; and that it does not check coach overlap, coach must-keep rules, daylight, closures, permits, travel, saved exceptions or teams whose practice time is TBD, so a run can place fewer practices than it shows. The teams counted are the roster, so a team the last run lost is still counted. It reads four tables as the signed-in user, all or nothing: a failed read names its table and draws no row, and until the reads arrive (and again after the page saves) it says "not checked yet". The "still needed" arithmetic is held equal to the Edge planner's own over one shared league.

- **The Exports page has three read-only reports over the saved game schedule: a Day Sheet, a coach's schedule and "Changes since publication", each with a CSV** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 7 of 13; owner decisions of 2026-11-06; no migration, no Edge change, nothing is written). **Schedule reports**, below the files, is read when it is opened. The **Day Sheet** takes a date and an optional venue (chosen by id: two venues can share a name) and lists each saved game once, the TIME TBD games apart; its rows are the master export's for the same date and venue, half as many because the export writes a game for each team. The **coach schedule** lists a coach's games and practices across every team they have now, head and assistant, with a clash column (the schedule check's coach conflict for games, read week by week; one rule for practices, the same weekday at overlapping times on shared dates; a practice is never compared with a game) and a marker for a coach on more than one team, counted from the team list and not from the flag on the Coaches page. **Changes since publication** compares a chosen published baseline with the saved schedule and lists every game that changed, was cancelled or is new, with the reason recorded when changes were allowed; because a baseline records each game's teams, slot and week and not which game is which, a game moved to another slot or week shows as one game no longer saved and one game new, and the page says it does not link them. Names only: no email or phone is read. A table that fails to read is named and nothing is drawn; a view still waiting says "Not checked yet". The coach schedule needs no game run (it lists practices, the marker and the practice clash, and says there are no games), reads the coaches and practices apart from the league so a failure there blocks that report only, and says how many practices have temporary changes it does not apply (the Exports panel's own warning: the clash column is computed on the weekly series). The store hook `usePublicationBaselines` gains `readBaseline` (its read and integrity re-check of one baseline, now also used by `compareWithBaseline`).
- **The Games page shows Published: a switch on each saved game, a bulk bar, an "Allow changes" dialog and a history, and the Exports upload can mark its games Published** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 3 of 13; owner decisions of 2026-11-06; no migration). Every saved game says whether it is Published, has changes allowed or is not published, in words and on a switch named "Published: home versus away"; turning it on needs nothing. A Published game has no grip and no "Move to", and a drop or a move that reaches the page is refused with a sentence; the database refuses regardless. A bar above the schedule counts "N of M saved games Published, K with changes allowed", filters the list by each, and publishes or allows changes for all games, one division, one date or one venue, counted before anything is sent from the saved schedule and never from a filtered list. "Allow changes" asks for a reason from a short list, an optional note of at most 200 characters ("Do not enter player names or other personal information"; the note stays in the audit history until the retention job clears it) and one tick; a refusal is shown in the database's words. A game's History shows who published it and every time changes were allowed. The Exports panel's upload has "Mark these games Published", on by default, which marks exactly the games in the files after checking them against the saved schedule read fresh (files made before another tab applied a change are refused, and must be generated again), and is off for a completed season, whose export still finishes. A change whose answer was lost is read back rather than assumed, and focus is put back after a change that removes the row it was on. **A game moved to another slot or week is saved as a new game that starts not Published** (the save identifies a game by its teams, slot and week), and the page says so when the move is staged and applied. _(Superseded by the F11-1 entry above: a moved game now keeps its id, its Published state and its history, and the page's sentences say so.)_

- **Generating the schedule again keeps the Published games exactly where they are** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 2 of 13; no migration). The game generator takes the saved Published games as `pinned`, treats each as a game already placed (it keeps its slot, its week and its sides, and its teams and coaches are busy at its time), skips the matchup it stands in for, and hands it back unchanged beside the new games; the Games page stages all of them and says "N Published games kept as they are". Games that are not Published are generated again as before, and one that no longer fits is listed as TIME TBD with its reason. With no Published game, or on a database that does not have the flag yet, the generator and the page do what they did. A game's row, and its id, survive a save only if it comes back in the same slot, week and sides, which is what keeping it means here.

- **The pure core of the practice import, and a placeholder practice schedule to test it on** (PR 9 of the schedule-expansion plan, `docs/changes/2026-11-03-schedule-expansion.md` section 4.11, which PR 1 adds; owner decisions of 2026-11-06; no migration, no Edge change, no persistence and no screen: nothing in the app calls it yet). `packages/core/src/practiceImport/` reads a flat CSV of practices, one row per timed cell: days, times (`12:00 AM`, `12:30 PM`), `End` or `Length` as wall-clock minutes (a practice has no clock to convert), a blank `Team` as an open slot, `Use = hold` as a cell that makes no slot, dates from the row, the confirm step or the season, and only the allowlisted columns. Its mapping proposes a team, division, location, field or half only on an exact single match; an optional alias file and the previous import's mapping are shown beside it and never applied without the admin, and an alias that disagrees with an exact match is shown with it, choosing neither. It turns rows into slots by the database's own supply rule (a whole field clashes with each half, back to back is allowed), flags a team on both halves of a field instead of merging it into a whole-field row, proposes each division's practices a week (the most common count; a tie proposes nothing) and practice length, and pairs a re-import's rows leaving and arriving at team level, with the new rows of a probable move unticked. `fixtures/practice-schedule-2026/` is 236 invented placements over 710 timed rows, generated by `scripts/build-practice-fixture.mjs` with eight counted plants and a pre-plant control.
- **Published games: a game can be held in place, and letting go of it is a deliberate, audited act (database and Edge half; no screen yet)** (`docs/changes/2026-11-03-schedule-expansion.md`, PR 1 of 13; owner decisions of 2026-11-06; migration `20261119010000_game_published.sql`). Each saved game gains a **Published** flag, off for every existing game. While it is on, nobody signed in can move the game, change its field, time or teams, or delete it, whatever the path (a save, a cancel, deleting its team or its slot); a save that leaves a Published game out is refused instead of quietly hiding it, and the Edge function answers it with a 409 `GAME_PUBLISHED` naming the games. Turning Published on needs nothing. Turning it off, "Allow changes", is open to any organization admin (staff included), takes a reason from a short list (`field-change`, `coach-request`, `conflict-fix`, `published-in-error`, `other`) and an optional note of at most 200 characters, works one game at a time or up to 2,400 at once, and writes one audit row per game with how the game stood. The Games page switch and the generator keeping Published games follow in later pull requests. Also in this change: the mock client mirrors the switch and the guard, a pure helper (`@squadlogic/core/gamePublished.js`) says the same rules in the app, and AGENTS.md section 3 records the owner's review policy (documentation and very minor pull requests need no review; every other one is reviewed by Codex first, then gets one `/code-review`).

Its mapping proposes a team, division, venue or field only on an exact single match (labels that differ by a word stay two; an ambiguous one is never mapped), knows outside clubs, and lists what a confirmed import would create. Its conflict audit asks the Games page's own report and says what it did not check: a team with no coach is "not judged", never "clear". `fixtures/schedule-2026/` is 574 invented games, generated by `scripts/build-schedule-fixture.mjs` with counted plants and a pre-plant control.
