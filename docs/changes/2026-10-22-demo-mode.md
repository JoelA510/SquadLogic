# Demo mode: try SquadLogic on a ready-made league

Kind: feature · Drawn up: 2026-10-22 against `origin/main` at `0e9fd31` · Owner: the repository owner
· Status: **agreed 2026-10-22** (decisions 1-6 and 8; decision 7, confirming `docs/product.md`, is open
and blocks nothing) (AGENTS.md rule 14: persistence, authentication and authorization, the scheduler; new
environment variables). Revised the same day for the Codex review of PR #638 (15 findings).

Every claim about the code is _statically reviewed_ (read) unless marked _executed_. The demo
league is `fixtures/demo-2026/` from PR #637, which this plan builds on. The product context is
`docs/product.md`, drafted with this plan for the owner to confirm.

## Why

A league administrator deciding whether SquadLogic fits their league can't judge it from an empty
account: the value is in what it does with a season's registrations. The demo hands them a full
recreational league (128 teams, 1,259 players, 251 coaches, all placeholders) to generate teams and
schedules with, for half an hour, without an account and without their own data (`docs/product.md`,
"Prospective league"). The same league is a realistic seed for the real-backend tests and for
staging. A public demo is not a "public club site" (AGENTS.md 2.1): it shows the product, not a
league's own pages.

## Behavior

- **Now:** a visitor without an account sees the sign-in page and can sign up and create an
  organization (`Login.jsx:289-308`, `initialize_new_tenant`), which starts empty.
- **After:**
  - The sign-in page offers **Try the demo** on a deployment that enables it.
  - One click gives the visitor a private copy of the demo league, with them as its
    administrator, without an email address:
    - the season;
    - divisions with teams and rosters;
    - coaches assigned;
    - fields and practice slots.

    Divisions are grouped into programs once Phase E2 has shipped (D3 depends on nothing from E).

  - A banner says it is a demo and how long is left. Five minutes before the end it warns. At 30
    minutes the visitor is signed out to a "your demo has ended" page with **Start again** and
    **Create an account**. The server refuses the demo from then on, whatever the browser does. The copy is deleted within ten minutes.
  - The demo's people (players, guardians, coaches, contacts) are read-only. Teams, rosters,
    schedules, fields and slots can be changed freely, so no visitor can type in a real child's
    details.
  - Trying to import a file opens a notice instead of the file picker. It offers to create an
    account on this deployment, or to run SquadLogic yourself, and names the official hosted
    service only on a deployment configured to.
  - U4 has four practice cohorts with one 30-minute session a week each, one at a time, at least
    15 minutes apart, and no games.

- **Unchanged:**
  - Sign-up, organization creation and invites for real accounts.
  - Every RLS policy and RPC as a real member of a real organization sees them.
  - The production build never falls back to the mock client (`tests/mockModeGuard.test.js` stays
    green, unedited).
  - A deployment that does not enable the demo shows nothing of it.

## Out of scope

- A client-only demo on the mock client (weighed below; decided against).
- Converting a demo into a real account; the data is placeholders, and "Create an account" starts
  empty.
- Previewing the demo as a coach: a later change (owner, 2026-10-22). As a guardian: not planned.
- `Payment Plan`: reading it as the registered program and division at import is Phase E's import
  mapping. Keeping the column without a reader would be a field parsed and unread (AGENTS.md,
  verification conventions), so D1 leaves it to E.

## Options

**A. Client-only demo on the mock client.** It needs no backend and costs nothing to run, but it
would show a different product:

- The scheduler, team generation and every save are Edge Functions the mock does not run. In a
  deployed build they go to localhost, which the CSP blocks.
- The mock would have to ship in production behind a new build flag, with the seven
  build-guarded RPC groups and the eight `IS_MOCK_MODE` constants turned into runtime state.
- It re-merges the whole store on every read, which won't carry 1,500 people.
- It would share `localStorage` (the auth token, `squadlogic_active_org`) with a real session on
  the same origin.
- Every RPC the product adds would need a mock twin before the demo shows it.

**B. A server-side demo organization (agreed 2026-10-22).** The real product on the real backend:

- The visitor signs in anonymously.
- One RPC copies the demo league into a new organization marked with its expiry.
- A `pg_cron` job deletes expired copies.
- RLS, the RPCs, the Edge Functions and the audit trail work unchanged, because a demo
  organization is an organization.

The costs:

- Anonymous sign-in must be enabled on the hosted project, and anonymous users must be fenced out
  of everything real (D3).
- Each live demo takes about 4-6 MB, so concurrent demos are capped (decision 2).
- Abuse is bounded by Supabase's per-IP limit, the cap of 10, and Turnstile CAPTCHA (decision 3).

## Design

### D1. Import fixes the fixture exposed (small; real users benefit first)

A prospective league's GotSport export has the same shape as the fixture, so these are fixed before
the demo invites them to make an account and import.

- **Coaches get a full name** when the export has only first and last name. The server composes
  `full_name` from `first_name` + `last_name` when it is absent, in `import-validation` before
  `validateRow`. The frontend `REQUIRED_HEADERS.coaches` accepts the pair, and the ColumnMapper's
  composition stays for other shapes.
- **A duplicated canonical key keeps the first non-blank value**, not the last value. This applies
  in `import-validation` and in ImportPanel's `buildPreview`, matching the ColumnMapper, which
  already keeps the first.
- **Not changed:** the sensitive-column filter (`Payment Plan` included, until Phase E reads it).
- **Tests:**
  - `tests/demoFixture.test.js`: the coach header check expects `[]` and the email-loss count
    expects 0.
  - A Deno mirror test of the composition and of first-non-blank.
  - `tests/importHeaders.test.js`: first/last satisfies coaches, and a missing last name still
    fails.

### D2. Practice-only divisions and reserved practice slots (medium; solver, schema)

- **Schema:**
  - `divisions.plays_games boolean NOT NULL DEFAULT true`.
  - `practice_slots.division_id uuid NULL`, a foreign key to `divisions` in the same organization
    (composite, as Phase E's `programs` will be).
  - A slot with a division is used only by that division's teams. A division with reserved slots
    uses only those.
- **Writers** (each audited as its neighbours are):
  - `admin_upsert_division_settings` takes `plays_games`.
  - A new `admin_set_practice_slot_division(slot_id, division_id)` RPC, behind a division select
    on each slot in Field Management, sets or clears a reservation.
  - The fields CSV gains an optional `division` column, resolved by name within the season in
    `finalize_field_import_job`; an unknown name fails the row with its reason.
- **Overlap and turnover refused at write.** The slot writers refuse a slot on the same bookable
  surface that overlaps another, or starts less than the turnover (default 15 minutes) after one
  ends. They compare only:
  - slots on the same surface: the same `field_subunit_id`, or, without one, the parent field and
    each of its subunits (the estate contract treats a subunit as narrower than its field);
  - on the same weekday;
  - whose `valid_from`/`valid_until` windows intersect.

  That is the first live enforcement of the turnover rule, at the point of writing.

- **Games:** `GameSchedulingPage` loads each division's current `plays_games` with the teams and
  carries it through `normalizeTeam`. `buildRoundRobinByDivision` skips `plays_games = false`
  divisions, and the page shows them as "practice only", not as unscheduled.
- **Practices:** core `schedulePractices` and the Edge solver honour slot reservation.
- `rosterSizing` no longer throws on a non-"NvN" format (the division's own roster limits apply).
- **Tests:**
  - `packages/core` unit tests: a `plays_games = false` division gets no fixtures and is not
    counted unscheduled; reserved slots go only to their division; four U4 cohorts in four
    reserved 30-minute slots 45 minutes apart each get one.
  - The page path, not just the core: `tests/gameSchedulingPracticeOnly.test.jsx` renders
    `GameSchedulingPage` over a team-run summary and division settings from the mock, with U4
    `plays_games = false`, and asserts no U4 fixtures and U4 listed as practice only. This fails
    while the flag does not reach the page.
  - pgTAP `practice_only_divisions.sql`:
    - the writers' refusals: an overlapping slot, and one starting 10 minutes after another;
    - that two halves of one field (two subunits) may run at once;
    - that slots whose effective windows do not intersect never conflict;
    - an unknown division in the CSV;
    - the audit rows.
  - The season-2026 fixture suite stays green (AGENTS.md, scheduling conventions).

### D3. The demo organization (medium-large; migrations, RPCs, cron)

- **Data:**
  - `organizations.demo_expires_at timestamptz NULL` (set means demo) and `demo_owner uuid NULL`.
  - **Expiry is immutable from clients.** A `BEFORE UPDATE` trigger on `organizations` refuses
    any change to `demo_expires_at` or `demo_owner` when `current_user` is `authenticated` or
    `anon`: a client's update runs as one of those roles, while `start_demo_session` and
    `purge_expired_demos` run as their definer. "Organizations: admins update" would otherwise let
    the demo's own admin clear its expiry.
  - A `demo_seed` schema, not exposed to PostgREST, whose tables hold the league as the fixture
    shapes it: season, divisions (U4 with `plays_games = false`), teams, players, guardians,
    coaches, assignments, fields, and practice slots including the four U4 sessions reserved to
    U4. No programs: when Phase E2 ships, it adds them to the seed, as its backfill does for
    every season.
  - `demo.started` is registered in `audit_actions` by the same migration.
- **Seed generation:**
  - Its insert migration is generated from `fixtures/demo-2026/*.csv` by
    `scripts/build-demo-seed.mjs`.
  - A Vitest drift test regenerates it and compares, so the seed and the fixture cannot diverge
    and nobody hand-edits the SQL.
- **`start_demo_session()`** (SECURITY DEFINER):
  - **Serialized:** it takes `pg_advisory_xact_lock` on one key for demo creation before any
    check, so the cap and the one-per-user rule are judged one caller at a time. A unique partial
    index on `organizations (demo_owner) WHERE demo_expires_at IS NOT NULL` makes a second live
    demo for one user impossible even if the lock is ever bypassed.
  - **Refuses:**
    - a caller who is not anonymous (`auth.jwt()->>'is_anonymous'`);
    - when the number of live demos is at the cap (decision 2), with a clear "try again in a few
      minutes".
  - **Returns** a caller's existing live demo instead of creating another.
  - **Creates**, in one transaction:
    - the organization, named "Demo league", expiring 30 minutes later;
    - the caller as its admin;
    - a copy of every `demo_seed` table with fresh ids;
    - one `demo.started` audit row.
  - **Returns** the organization id and expiry.
- **Expiry enforced by the server.** `is_org_member` and `is_org_admin` return false for an
  organization whose `demo_expires_at` has passed. Every RLS policy and RPC that asks them then
  refuses the demo at expiry, between expiry and purge, whatever the client does. The cost is
  one join to `organizations` per helper call; D3 measures it on the seeded league.
- **Fencing** (each a refusal with a pgTAP case):
  - Anonymous callers are refused by `initialize_new_tenant`, `create_org_invite`,
    `redeem_org_invite` and `set_my_contact_card`.
  - **People writers refuse demo organizations**: every function that writes `players`, the
    guardian links, `coaches` or contact details (`admin_update_player` and its siblings, the
    coach and guardian writers). The pgTAP finds them from the catalogue: functions granted to
    `authenticated` whose body writes those tables, by `pg_proc.prosrc`. It requires each to refuse
    a demo organization, so a new people writer cannot slip past. The people pages show the
    records read-only in a demo.
  - Every import path refuses a demo organization: `create_import_job`, the finalize RPCs, and
    `import-validation` (`organization_id` is a demo).
  - The `exports` bucket's insert policy refuses a demo organization's folder. A storage delete
    from SQL leaves the bytes behind, so no object may be created that a purge would have to
    clean.
  - The pgTAP enumerates every RPC granted to `authenticated` and requires each to be on an
    "allowed for anonymous" list or to refuse anonymous callers. The universe comes from the
    catalogue, not from this plan.
- **`purge_expired_demos()`** (definer, not granted to any client role):
  - Deletes expired demo organizations, and with them every org-scoped row.
  - Deletes the anonymous `auth.users` with no remaining membership.
  - Records the counts in `demo_purge_log`.
  - `pg_cron` runs it every 10 minutes.
  - The pgTAP seeds a demo, expires it and purges it. It then requires no row in any table with an
    `organization_id` column (enumerated from `information_schema`) to name it, and no `auth.users`
    row for its user.
- **Purge health, watched outside the database.** A scheduled GitHub Actions workflow (hourly, as
  the retention workflow is) calls a read-only `demo_health()` RPC with the service key. It fails
  the run when:
  - an expired demo organization is more than 30 minutes past its expiry, or
  - the newest `demo_purge_log` row is more than 30 minutes old.

  A failed run opens or updates a GitHub issue, as "Report a failing scheduled audit" already does
  for the audit workflow. The workflow is proved against a planted stale log in its own test.

- **Tests**, all pgTAP `demo_sessions.sql` plus the dblink smoke:
  - a demo admin's `UPDATE organizations SET demo_expires_at = NULL` is refused;
  - two concurrent `start_demo_session()` calls from one user give one organization, and a burst
    at the cap from different users never exceeds it (smoke with `dblink`, the pattern
    `docs/sql/20261021030000_smoke.sql` uses for lock races);
  - `demo.started` is registered and its row written;
  - after expiry and before purge, a member's read of the demo's players returns nothing and a
    write is refused;
  - each people-writer family and each import path refuses a demo; the anonymous fences hold;
  - the purge leaves no org-scoped row.
- **Rollback:** revert and smoke scripts under `docs/sql/` as for every migration. The revert
  drops the cron job first, then deletes demo organizations and drops `demo_seed`, the trigger and
  the columns.

### D4. The demo in the app (medium; UI, env)

- **Environment** (through `env.js`, `envRules.js`, `.env.example` and `ENVIRONMENT.md`, held by
  `tests/env.test.js`):
  - `VITE_DEMO_ENABLED`: `true` shows the entry point. It is unset on a self-hosted deployment,
    whose backend may not allow anonymous sign-in.
  - `VITE_OFFICIAL_SITE_URL`: an optional http(s) URL, set only on the official deployment's
    Vercel project. When it is set and is not the current origin, the import notice can say
    "SquadLogic is also hosted at …".
  - `VITE_TURNSTILE_SITE_KEY`: the public Turnstile site key (the secret lives only in the
    Supabase project's CAPTCHA settings). Unset, no widget renders and no token is sent, which
    suits a self-hosted project with CAPTCHA off.
  - The official domain appears in no source file. A test greps `frontend/src` for it, and the
    one existing source mention (`env.js:59`, a comment naming `squadlogic.vercel.app`) is rewritten
    in the same PR.
- **Entry, outside the sign-in page's lifecycle.**
  - **Button:** **Try the demo** navigates to `/demo/start`, a route rendered for signed-out and
    anonymous users alike, outside the redirect that sends a user with no organization to
    `/organizations/new`.
  - **Startup:** the route shows the Turnstile widget; once it yields a token the component calls
    `signInAnonymously({ options: { captchaToken } })` and then `start_demo_session()`, then opens
    the dashboard on the demo organization.
  - **Failure:** on any failure (the cap is reached, anonymous sign-in is disabled, the RPC
    errors) it signs the anonymous session out and stays on `/demo/start` with the error
    announced.
  - **Anonymous users are kept on the demo.** An anonymous session is never routed to
    `/organizations/new`: the app routes it to its demo, or to `/demo/start`.
- **Banner:** a persistent banner in the top bar with role `status`:
  - It reads "Demo league: resets in 22 min", and offers **Leave demo**.
  - At five minutes an `aria-live="polite"` warning appears.
  - At expiry the app signs out and routes to `/demo/ended`, with **Start again** and **Create an
    account**. A refusal from the server at expiry routes there too.
  - It uses the existing tokens in both themes, is keyboard-operable, and passes axe.
- **Turnstile everywhere Supabase asks for it.** CAPTCHA is a project-wide Supabase setting:
  once on, sign-in, sign-up and password reset also need a token (Supabase docs, "Enable CAPTCHA
  Protection"). So the widget goes on `Login`'s sign-in and sign-up forms and the password-reset
  form too, each passing `captchaToken` and resetting the widget after the call.
  - **No new dependency:** a small component loads Cloudflare's script
    (`https://challenges.cloudflare.com/turnstile/v0/api.js`, explicit render) only on the pages
    that need it.
  - **CSP:** `script-src` and `frame-src` allow `https://challenges.cloudflare.com` in
    `vercel.json`, with `docs/security/csp.md` kept in step (`tests/cspPolicy.test.js`).
  - **Accessibility:** the widget's own label is kept, and a failed challenge is announced with a
    retry.
- **Read-only people:** in a demo organization the player, coach and guardian pages hide their edit
  controls (the server refuses them anyway, D3).
- **Import intercept:**
  - In a demo organization, `validateAndReadFile` and the drop zone open a dialog, with focus
    trapped and restored on close.
  - The dialog says the demo holds placeholder data only. It offers **Create an account here**
    (signs out of the demo and opens sign-up) and **Run your own SquadLogic** (the self-hosting
    guide in the public repository, `docs/operations/self-hosting.md`). With

## Risks and rollback

- **Risk:** an anonymous user reaches something real.
  - **Watch:** the D3 pgTAP catalogue checks fail on any new client-callable RPC that does not
    decide, and on any new people writer that does not refuse a demo.
  - **If it happens:** the RPC refuses anonymous callers or demo organizations before release.
- **Risk:** the purge stops running and demos pile up toward the 500 MB threshold.
  - **Watch:** the hourly health workflow fails and opens an issue (D3).
  - **If it happens:** run the purge by hand through the service role, and fix the job.
- **Risk:** a burst of demos hits the cap.
  - **Watch:** the RPC's refusals are logged with a count.
  - **If it happens:** raise the cap if there's room, or add CAPTCHA.
- **Risk:** the expiry check in the membership helpers slows every query.
  - **Watch:** D3 measures it on the seeded league.
  - **If it happens:** keep the check in the helpers, served by an index on
    `organizations (id) WHERE demo_expires_at IS NOT NULL`.
- **Risk:** the seed drifts from the fixture.
  - **Watch:** the drift test.
  - **If it happens:** regenerate.
- **Rollback, in this order** (D3 depends on D2's columns):
  1. Set `VITE_DEMO_ENABLED` unset: the entry point disappears with no deploy of data.
  2. Disable anonymous sign-in.
  3. Revert D3 with its script, which drops the cron job, deletes demo organizations, and drops
     `demo_seed`, the trigger and the columns.
  4. Only then revert D2, if wanted.

  D1 reverts independently.
