# Registration state, division capacity and optional balancing data

Feature plan for B5.10. Proposed November 24, 2026. The owner decides when to build. C11 delivers this plan.

## Why

A league administrator needs to know which registrants can be teamed and how many more can fit in each division. Leagues that collect experience but do not rate players want to use years played when balancing teams. The owner's source signal is the registration platform's Waitlist column. Both the team and the registration decision have consequences for families, so each proposed import change should be visible before it takes effect. [Owner answers, B5.10](2026-11-03-schedule-expansion.md) · [Product brief](../product.md)

## Recommended behavior

1. **Mapping and reimport.** Offer optional player destinations for Waitlist, Years Played and Coaching Interest in the existing mapper. Show the proposed source and its meaning before Apply. Preserve the supported true spellings and their explicit false counterparts. When multiple columns claim one destination, require the admin to select the authoritative source. An unknown nonblank waitlist value requires correction or deliberate exclusion of that row. A blank or absent value on a new player uses the existing active default and is counted as unspecified in preview. On a matching player it preserves status. An explicit false releases a waitlisted player, and an explicit true marks an eligible active player as waiting. Preserve independent inactive or pending states unless changed through their existing workflow. When the organization explicitly disables Waitlist, explain why the mapping has no effect and preserve existing records on reimport. Show a count of proposed status transitions before applying, including a file value that would change a prior admin decision.
2. **Division headroom.** Show every selected-season division using the complete, paged enrollment and saved rosters. A narrow follow-up import must not shrink the universe. For saved teams calculate open seats from each team's applicable division limit and its actual roster. Display any recorded per-team limit with its source if the saved run used a different limit. Count each occupied seat once, including retained waitlisted seats. Reserve room for eligible, unseated registrants using the engine's effective division and age rules. Report free seats, already-eligible demand, additional places or shortage, and waitlisted count separately. For example, two teams capped at eight with ten seated and two other eligible players have six open seats and room for four additional registrants. Three waiting registrants appear beside that estimate. Admitting them requires a separate action. When a saved team is already over its maximum, display its excess separately and preserve its roster.
3. **Projection before teams exist.** Show the chosen or recommended team count, maximum per team, eligible count and assumptions. Label the result as projected. A finite configured team ceiling can support a separate maximum estimate. When usable limits or enrollment are missing, show which input is needed. Treat zero eligible players as a known count. Keep a zero-team division visible and explain whether a finite planning limit exists. Coach anchors, eligibility and buddy constraints can reduce practical placements.
4. **Optional signals.** Compute availability per selected division and season. Give an explicit admin off value precedence. With an unset preference, enable an experience signal when valid years exist and spread coaching leads when there is at least one eligible, willing player and both relevant feature choices permit it. An explicit on with no usable values stays configured and displays why it is idle. Prefer an enabled, populated rating signal to years and use size when neither supplies usable values. A valid zero years is evidence. An omitted or invalid value contributes no evidence. Identify partial coverage and apply a neutral value for unknown players in balance scoring. A roster with no usable coaching leads can say exactly that. Historical false defaults alone cannot establish that every registrant answered the question. Keep operation-specific availability out of stored organization defaults.

## Design and tradeoffs

Reuse the allowlist and add canonical mapping before the browser, Edge, SQL and mock readers consume the file. Preview and finalization must use the same value classifications and transition rules. Guard the finalizer against a status transition that changed since confirmation. Repeat confirmation must preserve idempotency. Use tenant- and season-scoped admin RPCs, RLS, boundary validation and the existing audit path. Report aggregate transition and validation counts. Give errors a row number and field, and keep contact data out of logs. A completed season remains read-only.

For headroom, use one pure calculation with explicit inputs for the Teams view and any dashboard summary. Count from enrollment, the division registry and persisted membership. Cross-check saved roster identities and flag inconsistent source data before offering a numeric admissions estimate. Derive optional balancing from durable, usable inputs and the raw explicit choices, then pass the same effective policy to the board, fresh generation and incremental placement of new players. Preserve numeric rating, skill-tier mapping, coach anchors, buddy priority, roster limits and deterministic tie breaking. In an incremental run, keep prior team IDs and assignments of reviewed, published or locked players.

Adding a parallel registration-state or experience column would require backfill and conflict resolution on every import. Reusing the existing fields avoids that divergence. Rewriting global feature flags on each upload would let one partial file change another division's behavior. Runtime availability preserves explicit settings and supports mixed divisions. Merely relabelling the dashboard's occupied-seat percentage would still omit active demand and divisions without teams.

## Scope, risks and rollback

This is a multi-PR domain and persistence change under AGENTS.md §3, rule 14. The owner must approve implementation. Existing privacy, tenancy and import-contract rules apply. Payment state, paperwork, family contacts, new account roles, cleanup of the three legacy columns and new registration forms are outside the feature. The plan proposes no new dependency, service, environment variable or player field.

A changed parser can release a waiting player, a partial roster read can overstate places, and a new signal can move reviewed players. Halt the affected slice if the independent counts disagree, a scoped query is incomplete, or the frozen-roster fixture changes. For a future writer change, use one guarded migration in its PR with smoke and revert scripts. Run the base hashes against the read-only project connector and let CI deploy. Reverting code can restore the old parser. It cannot reconstruct previous player choices from aggregate counts. Preserve the existing import rollback contract and document any transition it cannot reverse before shipping that writer.
